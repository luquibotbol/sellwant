## What exists

SellWant lets people post a ticket or a request for one, negotiate in public, and lock a price. The two parties then see each other's contact/payment handles. The buyer says they paid and later confirms receipt. The app records those statements; it does not currently verify a payment. A Cloudflare Worker serves the web export, publishes active listings for discovery, and drains transactional offer emails.

## Flow and authorization evidence

1. `useSession` observes Supabase auth; screens use `services/data.ts`. Public browsing handles absent sessions. Auth recovery validates internal return URLs.
2. Listing and offer writes attach the current user ID. The checked-in August 18 policy requires `from_user = auth.uid()`, an active listing, an unsuspended user, and a valid counterparty parent when the poster counters. It revokes broad offer updates and grants only status updates. This verifies file contents, not deployment.
3. `acceptOffer` invokes `accept_offer({p_offer_id})`; `createLockIn` directly inserts buyer/seller IDs and listing price. Actual role checks, price validation, row locks, unique constraints and grants are NOT in migrations. Historical specs describe them; those claims need a schema export.
4. `advanceDeal` invokes `advance_deal({p_lock_in_id,p_to})`. Existing states include dormant `code_released`; UI drives pending_payment → paid → confirmed or cancelled. `paid` means the buyer's claim. Specs/tests describe buyer-only advancement, participant cancellation, idempotency and listing recovery. They were not executed against a database during this audit.
5. Deal/contact reads rely on RLS, not UI authorization. Test as an unrelated user and anonymous caller before claiming privacy verified. Never give an external agent a service-role key.

The seven checked-in migrations are incremental patches, not a reproducible initial database. No `supabase/config.toml`, base schema, seed setup, or `accept_offer`/`advance_deal` definition exists. Do not invent replacement core SQL from old design documents.

## PayPal feasibility and verification boundary

[Direct merchant authorize/capture](https://developer.paypal.com/v5/checkout/auth-capture) is the smallest sandbox proof: the synthetic seller is the merchant owning the app. It does not prove arbitrary marketplace seller routing. [Partner integration](https://developer.paypal.com/platforms/checkout/standard/customize/auth-capture/) requires approved partner status and seller onboarding. Verify intended payee explicitly; never collect platform money and call it P2P or escrow. First demo is restricted to the configured sandbox merchant until multi-seller onboarding is proven.

Authorization lasts up to 29 days; the recommended capture honor period is 3 days, and capture can still fail. Keep demo lock/handoff deadlines short; PayPal expiry does not reopen a SellWant listing. Merchant fees can apply; remove zero-processing-fee promises from sandbox-enabled product copy before release. These are provider constraints, not a promise of account eligibility. [PayPal auth/capture guidance](https://developer.paypal.com/v5/checkout/auth-capture), [partner requirements](https://developer.paypal.com/platforms/checkout/standard/customize/auth-capture/).

Use stable, persisted request IDs with provider retention limits; reconcile unknown outcomes before retrying. [PayPal idempotency](https://developer.paypal.com/api/rest/reference/idempotency/). Verify webhook signatures using the provider API, store unique event IDs, and refetch authoritative resources before transitioning. [Official webhook specification](https://github.com/paypal/paypal-rest-api-specifications/blob/main/openapi/notifications_webhooks_v1.json).

Invoicing is only a fallback if authorize/capture is infeasible. Immediate invoice payment charges before the door handoff and would require an explicit changed journey/refund policy; it cannot silently replace a hold.
